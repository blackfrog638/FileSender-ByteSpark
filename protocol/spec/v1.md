# XnnTransfer Wire Protocol v1.0

Status: proposed normative specification.

This document specifies the XnnTransfer v1.0 wire framing and transfer
semantics for an established paired peer. Pairing, authentication, encryption,
and content-commitment algorithms belong to ADR 0002. The exact production
ALPN and security-profile identifiers, first-pairing controls, pre-trust
limits, and reconnect boundary are registered by `pairing-v1.md`. An
implementation MUST NOT claim production v1 conformance until the
prerequisites in [Security boundary](#security-boundary) are met.

The key words MUST, MUST NOT, REQUIRED, SHALL, SHALL NOT, SHOULD, SHOULD NOT,
RECOMMENDED, NOT RECOMMENDED, MAY, and OPTIONAL are to be interpreted as
described in BCP 14 when, and only when, they appear in all capitals.

## 1. Terminology and transport

- A **connection** is one ordered, reliable byte stream carried inside the
  security profile's TLS channel under exact ALPN `xnn-transfer/1`. It begins
  as a **provisional authenticated channel** after TLS completes and the active
  paired peer pin is verified. It becomes an **established protected
  transport** only after section 6 negotiation and channel binding complete.
- The **initiator** is the endpoint assigned that role by
  the provisional authenticated channel; the other endpoint is the
  **responder**. The protocol does not infer roles from IP addresses, ports,
  discovery data, or peer names.
- A **stream** is a logical transfer identified by a nonzero `stream_id`.
  Stream zero is the connection-control stream.
- A **transfer ID** is an opaque 16-byte identifier scoped to the authenticated
  peer pair. The original sender generates it from an approved cryptographic
  random source and MUST NOT reuse it for that peer scope. It survives
  reconnects; a `stream_id` does not.
- A **commitment** is an opaque byte string produced and verified by the
  approved `SecurityProfile`. v1 only frames commitments and does not define
  their algorithm.
- A **local policy limit** is an implementation or user limit no greater than
  the hard protocol limit.

The channel MUST preserve byte order and MUST report an unambiguous close. v1
does not run over unordered datagrams. A sender MUST NOT send a v1 frame until
the provisional authenticated channel is ready. Before the protected transport
is established, only the negotiation and binding controls in section 6 are
allowed.

## 2. Security boundary

ADR 0002 owns the concrete pairing, TLS, exporter, and finished-value
algorithms. This wire specification does not replace or modify those choices.
`pairing-v1.md` registers security profile `0x0001`, the byte-exact
established ALPN, first-pairing protocol separation, certificate ceilings, and
pre-trust policy. This specification consumes that profile through this
abstract lifecycle:

```text
SecurityProfile.open_provisional(peer_candidate)
  -> pinned, mutually authenticated TLS byte stream
  -> authenticated peer_scope
  -> initiator or responder role
  -> profile_context required by ADR 0002
  -> ProvisionalAuthenticatedChannel

SecurityProfile.bind_transport(
  ProvisionalAuthenticatedChannel,
  normalized_negotiation,
  raw_negotiation_transcript)
  -> role-specific transport_finished value

SecurityProfile.verify_peer_transport_finished(...)
  -> EstablishedProtectedTransport
```

The provisional channel protects negotiation bytes with pinned TLS, but it is
not yet an established v1 transport. Merely carrying negotiation inside TLS is
not the v1 downgrade defense. The `SecurityProfile` MUST bind both the
normalized negotiation and the exact raw transcript defined in section 6 to
the ADR 0002 transport context, then generate and verify the role-specific
finished values. v1 reaches `ESTABLISHED` only after the local finished value
has been sent and the peer's value has been verified.

The security profile also owns manifest, file, chunk, and prefix commitments
and peer-bound resume authorization. Their algorithms, domain separation,
canonical inputs, key lifecycle, and lengths remain defined by ADR 0002 and
its approved profile, not by this framing document.

The pairing ALPN `xnn-transfer-pairing/1` and `XNNP` frames are never legal on
this transport. An unknown, unpaired, revoked, corrupt, or pin-mismatched peer
fails before this state machine begins; there is no automatic fallback to
first pairing.

1. The cleartext bytes under `protocol/testdata/v1/` are deterministic parser
   fixtures only. They do not instantiate a TLS channel, exporter, or valid
   finished value and MUST NOT carry real metadata or content.
2. Discovery establishes reachability only and MUST NOT supply authenticated
   identity, protocol role, acceptance, or resume authority.
3. A provisional channel accepts only `HELLO`, `NEGOTIATE`, `NEGOTIATE_ACK`,
   `TRANSPORT_FINISHED`, and connection-scoped `ERROR` in the states defined by
   section 7.
4. Every byte of negotiation, binding, control, metadata, and content MUST
   remain inside the approved TLS channel. Protecting only file chunks is
   non-conforming.
5. A security, channel-binding, or authentication failure MUST close the
   channel without a
   protocol `ERROR`; emitting attacker-controlled diagnostics could create an
   oracle.
6. File offers, paths, sizes, commitments, contents, resume state, and transfer
   commands MUST NOT be parsed, accepted, persisted, or exposed to the UI
   before both transport-finished conditions are satisfied.
7. There is no cleartext, unauthenticated, unbound, or lower-security fallback.

## 3. Integer and text representation

All integers in headers, TLV headers, and integer TLV values use unsigned
network byte order (big-endian). No native structs may be copied directly to
or from the wire.

`UTF8` values MUST be shortest-form, well-formed UTF-8. Surrogates, overlong
encodings, U+0000, and Unicode noncharacters are invalid. Human-readable
strings SHOULD be NFC-normalized. Paths have stricter rules in section 11.

Sizes count octets, not characters. Arithmetic used for lengths, offsets,
counts, and totals MUST be checked before addition or allocation.

## 4. Frame format

Every frame is a fixed header, optional header fields, then exactly
`body_length` body octets.

| Offset | Width | Field | v1.0 rule |
| ---: | ---: | --- | --- |
| 0 | 4 | `magic` | ASCII `XNNT` (`58 4e 4e 54`) |
| 4 | 2 | `header_length` | 28 through 256 |
| 6 | 1 | `version_major` | 1 |
| 7 | 1 | `version_minor` | 0 during negotiation; selected minor afterward |
| 8 | 2 | `message_type` | section 8 |
| 10 | 2 | `flags` | zero in v1.0 |
| 12 | 4 | `stream_id` | zero for connection control; otherwise nonzero |
| 16 | 8 | `message_id` | per-direction sequence number |
| 24 | 4 | `body_length` | 0 through 1,048,576 |
| 28 | variable | header TLVs | `header_length - 28` octets |
| `header_length` | variable | body TLVs | exactly `body_length` octets |

The total encoded frame length is `header_length + body_length`; its hard
maximum is 1,048,832 octets. v1.0 defines no header TLVs, so senders MUST use
`header_length = 28`. Receivers apply the unknown-field rules in section 5 to
future header TLVs.

`message_id` starts at 1 independently in each direction and increments by
exactly one for every frame, including `PING`, `PONG`, and stream errors. Zero,
gaps, duplicates, wraparound, and reordering are connection-fatal
`MESSAGE_ID_VIOLATION`s. An endpoint MUST send `GOAWAY` and reconnect before
the next value would exceed `2^64 - 1`.

All v1.0 flag bits are reserved. A nonzero flag is a connection-fatal
`MALFORMED_FRAME` unless a future negotiated minor version or capability
defines it.

Before allocating or waiting for a body, a receiver MUST validate the complete
28-octet fixed header, `header_length`, `body_length`, checked total length,
version, flags, type, stream scope, and `message_id`. It MUST NOT drain an
oversized declared frame.

## 5. TLV fields

Header extensions and message bodies use the same TLV encoding:

| Offset | Width | Field |
| ---: | ---: | --- |
| 0 | 2 | `field_id` |
| 2 | 1 | `wire_type` |
| 3 | 1 | `field_flags` |
| 4 | 4 | `value_length` |
| 8 | variable | `value` |

Wire types are:

| Value | Name | Required value length |
| ---: | --- | ---: |
| 1 | `U8` | 1 |
| 2 | `U16` | 2 |
| 3 | `U32` | 4 |
| 4 | `U64` | 8 |
| 5 | `BYTES` | schema-defined |
| 6 | `UTF8` | schema-defined |
| 7 | `BOOL` | 1; value is exactly 0 or 1 |

`field_flags & 0x01` is `CRITICAL`; all other bits are reserved and MUST be
zero in v1.0. Required fields MUST carry `CRITICAL`. Optional fields MUST NOT
carry `CRITICAL` unless their semantics are required to process the message.

Fields MUST be encoded in nondecreasing `field_id` order. A known field may
repeat only when its message schema says `repeated`; repetitions MUST be
adjacent. An older receiver skips adjacent repetitions of an unknown
noncritical field because it cannot know the future field's cardinality.
Capability values MUST be unique and sorted numerically. Every body MUST end on
a field boundary and contain at most 256 fields.

A receiver:

- MUST reject an unknown critical field with `UNKNOWN_CRITICAL_FIELD`;
- MUST validate then skip an unknown noncritical field;
- MUST reject a reserved wire type or field flag;
- MUST reject a missing required field, wrong wire type or length, prohibited
  duplicate, out-of-order field, invalid Boolean, or trailing octet as
  `MALFORMED_MESSAGE`.

Unknown noncritical fields remain part of any protected transcript or
commitment over their containing object. Skipping a field never means removing
it before verification.

## 6. Version, capability, and limit negotiation

During `NEGOTIATING`, only `HELLO`, `NEGOTIATE`, `NEGOTIATE_ACK`, and
connection-scoped `ERROR` are valid. During `BINDING`, only
`TRANSPORT_FINISHED` and connection-scoped `ERROR` are valid. Negotiation frame
headers use version 1.0.

Each endpoint sends exactly one `HELLO`. Once both are received, the initiator
sends exactly one `NEGOTIATE`; the responder either returns an identical
`NEGOTIATE_ACK` selection or a fatal `ERROR`.

Version tuples are ordered lexicographically by `(major, minor)`. The initiator
MUST select the highest tuple present in both advertised inclusive ranges and
enabled by both endpoints' local policy. Selecting any lower tuple is
`DOWNGRADE_DETECTED`. No common tuple is `UNSUPPORTED_VERSION`. v1.0 endpoints
advertise only `(1, 0)` through `(1, 0)`. Version components in negotiation
fields are restricted to 0 through 255 so they fit the frame header; a major
version of zero is invalid.

A capability value is a `U32`: the high 16 bits are the capability ID and the
low 16 bits are its version. Advertising multiple versions of one capability
is invalid. v1.0 defines:

| Encoded value | Name | Rule |
| ---: | --- | --- |
| `0x00010001` | `BASE_TRANSFER_V1` | REQUIRED |
| `0x00020001` | `RESUME_V1` | OPTIONAL |
| `0x00030001` | `PARALLEL_FILES_V1` | OPTIONAL |

The selected capability set is exactly the sorted intersection of advertised
capabilities. It MUST include every capability required by either endpoint.
An unknown advertised capability may be ignored; an unknown required
capability causes `UNSUPPORTED_CAPABILITY`. `BASE_TRANSFER_V1` MUST be
advertised, required, and selected.

Negotiated receive limits are the minimum of the two advertised values. They
may lower but never raise the hard limits in section 10. Selection values MUST
exactly equal those minima.

### 6.1 Negotiation fields

`HELLO` fields:

| ID | Name | Type | Presence and constraint |
| ---: | --- | --- | --- |
| 1 | `min_major` | `U16` | required |
| 2 | `min_minor` | `U16` | required |
| 3 | `max_major` | `U16` | required |
| 4 | `max_minor` | `U16` | required |
| 5 | `endpoint_role` | `U8` | required; 1 initiator, 2 responder |
| 6 | `capability` | `U32` | required, repeated |
| 7 | `required_capability` | `U32` | required, repeated |
| 8 | `receive_max_body` | `U32` | required; 8,192 through 1,048,576 |
| 9 | `receive_max_in_flight` | `U32` | required; 1,048,576 through 67,108,864 |
| 10 | `receive_max_streams` | `U16` | required; 1 through 32 |

The advertised role MUST match the role supplied by the provisional
authenticated channel. Ranges with minimum greater than maximum are invalid.

`NEGOTIATE` and `NEGOTIATE_ACK` fields:

| ID | Name | Type | Presence and constraint |
| ---: | --- | --- | --- |
| 1 | `selected_major` | `U16` | required |
| 2 | `selected_minor` | `U16` | required |
| 3 | `selected_capability` | `U32` | required, repeated |
| 4 | `effective_max_body` | `U32` | required |
| 5 | `effective_max_in_flight` | `U32` | required |
| 6 | `effective_max_streams` | `U16` | required |

After the ACK is verified, all frame headers use the selected version.

### 6.2 Bound negotiation transcript

The ACK completes deterministic selection but does not establish the protected
transport. Both endpoints MUST construct the following two representations
before sending `TRANSPORT_FINISHED`:

1. `normalized_negotiation` is the ADR 0002 canonical representation of, in
   this exact semantic order:
   - the initiator role and every known initiator `HELLO` field, including the
     full offered and required capability lists and all receive limits;
   - the responder role and every known responder `HELLO` field in the same
     form;
   - every selected `NEGOTIATE` field, including version, the complete selected
     capability list, and all effective limits, after verifying that
     `NEGOTIATE_ACK` has identical field values.
2. `raw_negotiation_transcript` is the concatenation of four records in fixed
   role order, independent of network arrival order:

   ```text
   record(0x01, exact initiator HELLO frame)
   record(0x02, exact responder HELLO frame)
   record(0x03, exact NEGOTIATE frame)
   record(0x04, exact NEGOTIATE_ACK frame)

   record(tag, frame) = tag:U8 || frame_length:U32 || frame
   ```

   `frame_length` is big-endian and `frame` is the complete encoded frame from
   magic through the last body octet. Unknown noncritical TLVs, header
   extensions, flags, message IDs, and their original byte encodings remain in
   this raw representation. No accepted field or byte may be removed,
   reordered, or re-encoded before binding.

The `SecurityProfile` MUST bind both representations, together with the
profile context required by ADR 0002, into that ADR's TLS exporter transport
context. This document deliberately does not redefine the exporter label,
cryptographic construction, identities, nonces, session identifier, profile
identifier, or finished algorithm.

`TRANSPORT_FINISHED` is not part of either negotiation representation, avoiding
a transcript cycle. Each endpoint sends exactly one role-specific
`TRANSPORT_FINISHED` after the ACK and rejects a value received earlier, from
the wrong role, with the wrong profile-defined length, or failing
`SecurityProfile` verification. A replay, mismatch, or verification failure
closes the TLS channel without processing a transfer message.

## 7. Connection state machine

```text
PROVISIONAL_AUTHENTICATED
    | send/receive HELLO
    v
NEGOTIATING
    | initiator NEGOTIATE, responder matching ACK
    v
BINDING
    | local TRANSPORT_FINISHED sent and peer value verified
    v
ESTABLISHED ---------------------> DRAINING
    | fatal error / timeout          | streams terminal
    +-----------------------------+  v
                                  CLOSED
```

- `PROVISIONAL_AUTHENTICATED`: pinned TLS and the approved security profile are
  active, but application negotiation has not started.
- `NEGOTIATING`: only the negotiation messages allowed by section 6 are
  accepted.
- `BINDING`: deterministic selection is complete; only role-specific
  `TRANSPORT_FINISHED` and connection `ERROR` are accepted.
- `ESTABLISHED`: new transfer streams and control messages are accepted.
- `DRAINING`: entered after sending or receiving `GOAWAY`; no new stream is
  accepted, but existing streams may finish until the drain timeout.
- `CLOSED`: terminal. No bytes from this transport are processed.

A connection-scoped message not allowed in the current connection state, or
any transfer message received before both finished conditions transition the
connection to `ESTABLISHED`, is a connection-fatal `STATE_VIOLATION`.
Transfer-stream ordering errors after establishment use the stream-fatal rule
in section 13. A fatal connection error sends at most one `ERROR` if the header
and authenticated channel remain trustworthy, then closes.

Initiators allocate odd nonzero `stream_id` values; responders allocate even
ones. IDs increase by two, are never reused on a connection, and do not wrap.
The authenticated peer and transfer ID, not `stream_id`, identify a transfer
across reconnects.

## 9. Common and control bodies

Every field called required below is critical.

`ERROR`:

| ID | Name | Type | Constraint |
| ---: | --- | --- | --- |
| 1 | `code` | `U16` | required; section 14 |
| 2 | `fatal` | `BOOL` | required |
| 3 | `retryable` | `BOOL` | optional; default false |
| 4 | `offending_message_id` | `U64` | optional |
| 5 | `retry_after_ms` | `U32` | optional; at most 60,000 |
| 6 | `detail` | `UTF8` | optional; at most 256 octets |

Unknown or attacker-derived data MUST NOT be copied into `detail`. A receiver
MUST ignore `retry_after_ms` when `retryable` is false. `fatal` and `retryable`
MUST agree with section 14; a received Boolean cannot downgrade a mandatory
fatal error or make a non-retryable error retryable.

`PING` and `PONG` contain required `token` (`U64`, ID 1). A `PONG` MUST echo
the token. Each direction may have at most one outstanding `PING`. `GOAWAY`
contains required `code` (`U16`, ID 1) and optional
`last_accepted_stream_id` (`U32`, ID 2).

`TRANSPORT_FINISHED`:

| ID | Name | Type | Constraint |
| ---: | --- | --- | --- |
| 1 | `sender_role` | `U8` | required; 1 initiator, 2 responder |
| 2 | `verify_data` | `BYTES` | required; exact length and value defined by the selected `SecurityProfile`, framing hard limit 64 octets |

`sender_role` MUST match the role assigned by the provisional authenticated
channel and the sending direction. Only `SecurityProfile` output may populate
`verify_data`; protocol code and fixtures MUST NOT synthesize a production
value.

All transfer messages contain required `transfer_id` (`BYTES`, ID 1, exactly
16 octets). The transfer ID in every message MUST match the ID bound to its
stream.

## 10. Hard protocol limits

Local policy MAY impose lower limits and SHOULD do so based on available
memory, storage, and user settings. Peers MUST reject, not truncate, values
over an effective or hard limit.

| Resource | Hard limit |
| --- | ---: |
| Header length | 256 octets |
| Body length | 1,048,576 octets |
| TLV fields per header or body | 256 |
| Active transfer streams per connection | 32 |
| Unacknowledged content per transfer | 16,777,216 octets |
| Unacknowledged content per connection | 67,108,864 octets |
| Manifest entries per transfer | 100,000 |
| Aggregate encoded manifest path octets | 33,554,432 |
| Files plus directories per transfer | 100,000 |
| Total file bytes per transfer | 17,592,186,044,416 (16 TiB) |
| Bytes in one file | 17,592,186,044,416 (16 TiB) |
| File chunk data | 1,048,000 octets |
| Relative path | 1,024 UTF-8 octets |
| Path components | 32 |
| One path component | 255 UTF-8 octets |
| Human display name | 255 UTF-8 octets |
| Error detail | 256 UTF-8 octets |
| Commitment | 16 through 64 octets, further restricted by `SecurityProfile` |
| Resume authorization | 16 through 256 octets |
| Parallel open files | 16, and only with `PARALLEL_FILES_V1` |
| Retained resume state | 604,800 seconds (7 days) |

Counts and totals are checked both incrementally and against the values in
`TRANSFER_OFFER` and `MANIFEST_END`. A mismatch is `INVALID_MANIFEST`.

## 11. Offer and manifest

`TRANSFER_OFFER`:

| ID | Name | Type | Constraint |
| ---: | --- | --- | --- |
| 1 | `transfer_id` | `BYTES` | required; 16 octets |
| 2 | `entry_count` | `U32` | required; 1 through 100,000 |
| 3 | `total_file_bytes` | `U64` | required; section 10 |
| 4 | `manifest_commitment` | `BYTES` | required; 16 through 64 octets |
| 5 | `display_name` | `UTF8` | optional; 1 through 255 octets |

After an offer, the sender emits exactly `entry_count` `MANIFEST_ENTRY`
messages with contiguous indexes starting at zero, then one `MANIFEST_END`.

`MANIFEST_ENTRY`:

| ID | Name | Type | Constraint |
| ---: | --- | --- | --- |
| 1 | `transfer_id` | `BYTES` | required |
| 2 | `entry_index` | `U32` | required |
| 3 | `kind` | `U8` | required; 1 file, 2 directory |
| 4 | `relative_path` | `UTF8` | required; path rules below |
| 5 | `file_size` | `U64` | required; zero for a directory |
| 6 | `file_commitment` | `BYTES` | required for a file, absent for directory |
| 7 | `modified_time_ms` | `U64` | optional; untrusted presentation metadata |

Wire paths use `/` separators, are NFC-normalized, and are relative. They MUST
NOT contain an empty, `.`, or `..` component; a leading or trailing slash;
backslash; colon; C0/C1 control; Unicode noncharacter; or U+0000. Path
comparison for duplicate and ancestor checks uses the destination platform's
canonical case and normalization rules. Two entries that collide under those
rules, or a file used as another entry's ancestor, invalidate the manifest.
Symlinks, hard links, devices, sockets, alternate data streams, and absolute
or drive-qualified paths are not representable in v1.

`MANIFEST_END`:

| ID | Name | Type | Constraint |
| ---: | --- | --- | --- |
| 1 | `transfer_id` | `BYTES` | required |
| 2 | `entry_count` | `U32` | required; exact observed count |
| 3 | `total_file_bytes` | `U64` | required; exact checked sum |
| 4 | `manifest_commitment` | `BYTES` | required; equals offer commitment |

The receiver MUST verify all limits, paths, policy, available space, and the
profile-defined manifest commitment before accepting. It then sends exactly
one of:

`TRANSFER_ACCEPT`:

| ID | Name | Type | Constraint |
| ---: | --- | --- | --- |
| 1 | `transfer_id` | `BYTES` | required |
| 2 | `chunk_size` | `U32` | required; 4,096 through 1,048,000 |
| 3 | `initial_window` | `U32` | required; per-transfer credit, at least `chunk_size` and at most 16,777,216 |
| 4 | `resume_authorization` | `BYTES` | required iff `RESUME_V1` selected |
| 5 | `resume_retention_seconds` | `U32` | required iff resume selected; 1 through 604,800 |

`TRANSFER_REJECT`:

| ID | Name | Type | Constraint |
| ---: | --- | --- | --- |
| 1 | `transfer_id` | `BYTES` | required |
| 2 | `code` | `U16` | required |
| 3 | `retryable` | `BOOL` | required |
| 4 | `retry_after_ms` | `U32` | optional; at most 60,000 |
| 5 | `detail` | `UTF8` | optional; at most 256 octets |

Acceptance is explicit and applies only to the committed manifest. Discovery,
prior pairing, a prior transfer, or receipt of an offer is never acceptance.
Before sending `TRANSFER_ACCEPT`, the receiver MUST reserve its
`initial_window` from the connection-level credit budget defined in section 12.
It sends `BUSY` or a lower valid window instead of overcommitting that budget.

## 12. File data, flow control, and completion

`FILE_BEGIN`:

| ID | Name | Type | Constraint |
| ---: | --- | --- | --- |
| 1 | `transfer_id` | `BYTES` | required |
| 2 | `entry_index` | `U32` | required; a manifest file |
| 3 | `file_size` | `U64` | required; equals manifest |
| 4 | `chunk_size` | `U32` | required; equals accepted size |

`FILE_CHUNK`:

| ID | Name | Type | Constraint |
| ---: | --- | --- | --- |
| 1 | `transfer_id` | `BYTES` | required |
| 2 | `entry_index` | `U32` | required |
| 3 | `offset` | `U64` | required |
| 4 | `data` | `BYTES` | required; 1 through negotiated chunk size |
| 5 | `chunk_commitment` | `BYTES` | required |

Chunks for a file are sent in strictly increasing contiguous offset order.
`offset` MUST equal the receiver's next expected offset; every non-final chunk
MUST have the accepted chunk size. The checked sum `offset + data.length` MUST
not exceed the manifest file size. Empty files send no `FILE_CHUNK`.

Flow-control credit is directional. For each active transfer, its reservation
is its unacknowledged content plus its currently unused granted credit. The
connection reservation is the checked sum of those per-transfer reservations
over every active transfer stream in that sending direction. It MUST never
exceed `effective_max_in_flight`.

`TRANSFER_ACCEPT.initial_window` adds that amount to the connection
reservation. Sending content converts unused credit into unacknowledged
content without changing the reservation. Acknowledgement removes
unacknowledged content; a subsequent `window_increment` adds unused credit.
Terminal streams release their remaining reservation. Thus the sum of all
active initial grants and later increments, after subtracting acknowledged or
released credit, is connection-bounded even when transfers are accepted in
parallel.

The sender MUST keep unacknowledged data within both the per-transfer and
connection reservations. `CHUNK_ACK` contains `transfer_id` (ID 1),
`entry_index` (`U32`, ID 2), `next_offset` (`U64`, ID 3), and
`window_increment` (`U32`, ID 4), all required. `next_offset` acknowledges one
contiguous prefix. Before sending the ACK, the receiver MUST check that the
resulting per-transfer reservation is at most 16,777,216 octets and the
resulting checked sum across all active transfers is at most
`effective_max_in_flight`. A peer MUST reject a grant or content sequence that
would exceed either bound with `LIMIT_EXCEEDED`.

`FILE_END` contains `transfer_id` (ID 1), `entry_index` (`U32`, ID 2),
`file_size` (`U64`, ID 3), and `file_commitment` (`BYTES`, ID 4), all
required. The receiver verifies size and the profile-defined commitment over
the temporary file, then atomically commits it according to storage policy.

`FILE_COMMIT` contains required `transfer_id` (ID 1), `entry_index` (`U32`, ID
2), and `committed_size` (`U64`, ID 3). It is sent only after durable
verification and commit. An integrity mismatch is terminal
`INTEGRITY_FAILED`; it is never automatically retried.

Without `PARALLEL_FILES_V1`, only one file may be between `FILE_BEGIN` and
`FILE_COMMIT`. With it, up to the lower local limit, at most 16, may be open;
each file still uses contiguous offsets and the aggregate flow-control window.

After all files are committed, the sender sends `TRANSFER_COMPLETE` with
required `transfer_id` (ID 1) and `manifest_commitment` (`BYTES`, ID 2). The
receiver sends `TRANSFER_COMPLETE_ACK` with the same two fields only after all
destination commits are durable. The ACK is the successful terminal result.

## 13. Transfer state, cancellation, retry, idempotency, and resume

### 13.1 Transfer state machine

```text
OFFER -> MANIFEST* -> MANIFEST_END -> AWAITING_DECISION
                                           | reject
                                           v
                                        REJECTED

AWAITING_DECISION -> ACCEPT -> FILES -> COMPLETING -> COMPLETED
       |                |          |          |
       +----------------+----------+----------+--> CANCELLING -> CANCELLED
```

`FILES` consists of valid `FILE_BEGIN`, contiguous `FILE_CHUNK` and
`CHUNK_ACK`, `FILE_END`, and `FILE_COMMIT` subsequences. A stream-level
`STATE_VIOLATION` terminates that transfer. A connection remains usable unless
the error is classified connection-fatal in section 14.

### 13.2 Cancellation

Either endpoint may send `CANCEL` after `TRANSFER_OFFER` and before a terminal
result. It contains required `transfer_id` (ID 1), `code` (`U16`, ID 2), and
optional bounded `detail` (`UTF8`, ID 3).

The receiver of `CANCEL` MUST stop scheduling new I/O, make temporary output
unavailable, perform idempotent cleanup, and send `CANCEL_ACK`. The ACK
contains required `transfer_id` (ID 1) and `terminal_code` (`U16`, ID 2).
Cleanup may continue internally, but no callback may report success after a
cancelled terminal result.

Cancellation is idempotent. Repeated cancellation for a terminal transfer
returns the cached terminal code. If durable completion happened before the
receiver processed `CANCEL`, it reports `COMPLETED`; cancellation MUST NOT
delete committed output. Otherwise cancellation wins. The receiver's
authenticated terminal response is authoritative for simultaneous cancel and
complete races.

### 13.3 Idempotency and retries

The idempotency key is `(authenticated peer_scope, transfer_id)`.

- A repeated offer with the same manifest commitment and totals returns the
  cached decision or current state without creating files twice.
- Reuse of a transfer ID with different commitment, count, total, path, size,
  or content is terminal `IDEMPOTENCY_CONFLICT`.
- A repeated chunk at an already acknowledged offset is accepted only if its
  commitment and bytes match retained state; it is ACKed without a second
  write. Any mismatch is `IDEMPOTENCY_CONFLICT`.
- Accept, reject, cancel, file commit, and transfer completion responses are
  replayable terminal or progress facts and MUST be idempotent.
- Implementations retain terminal idempotency tombstones for at least 600
  seconds and no more than 604,800 seconds. Resume-capable tombstones and state
  use the accepted resume retention.

Frames are never retransmitted on the same ordered connection because
`message_id` forbids duplicates. An automatic retry requires a new provisional
authenticated channel, successful negotiation and transport binding, and
either `RESUME_V1` or a repeated idempotent offer.

Automatic retry is allowed only for transport loss, `TIMEOUT`, `BUSY`, or
`IO_FAILURE` explicitly marked retryable. It is forbidden for authentication
failure, protocol violation, unsupported version/capability, user/policy
rejection, cancellation, idempotency conflict, or integrity failure. A single
operation makes at most five automatic reconnect attempts over at most 120
seconds, with delays of 1, 2, 4, 8, then 16 seconds plus up to 25 percent
random jitter, while respecting a larger bounded `retry_after_ms`.

### 13.4 Resume

Resume requires negotiated `RESUME_V1`. On a newly established protected
transport and a new correctly allocated stream ID, the original sender sends
`RESUME_REQUEST`:

| ID | Name | Type | Constraint |
| ---: | --- | --- | --- |
| 1 | `transfer_id` | `BYTES` | required |
| 2 | `manifest_commitment` | `BYTES` | required |
| 3 | `resume_authorization` | `BYTES` | required; profile-defined and peer-bound |

The receiver verifies authenticated peer scope, authorization, commitment,
retention, and local state before revealing progress. It sends exactly one
`RESUME_STATE` for each original manifest entry whose `kind` is file, in
increasing `entry_index` order. Directory entries never produce
`RESUME_STATE`.

| ID | Name | Type | Constraint |
| ---: | --- | --- | --- |
| 1 | `transfer_id` | `BYTES` | required |
| 2 | `entry_index` | `U32` | required |
| 3 | `next_offset` | `U64` | required; verified contiguous prefix |
| 4 | `committed` | `BOOL` | required |
| 5 | `prefix_commitment` | `BYTES` | required when offset is nonzero and file not committed |

`RESUME_END` contains required `transfer_id` (ID 1), `entry_count` (`U32`, ID
2), and `status` (`U16`, ID 3). Here `entry_count` is the number of preceding
`RESUME_STATE` file-state messages, not the total manifest entry count. It MUST
equal both the observed number of `RESUME_STATE` messages and the number of
file entries in the original committed manifest. The sender MUST reject a
missing, duplicate, directory, out-of-order, or count-mismatched state as a
stream-fatal `MALFORMED_MESSAGE` before sending content.

Status zero means the listed state is resumable; `COMPLETED` means the transfer
already completed. Other terminal conditions use a stream `ERROR`. The sender
verifies each prefix under the profile before sending from `next_offset`.
Committed files are not rewritten. Missing, expired, mismatched, or
unauthorized local state returns `RESUME_UNAVAILABLE` without disclosing
whether a transfer ID exists.

| ---: | --- | --- |
| `0x0001` | `MALFORMED_FRAME` | connection-fatal, not retryable |
| `0x0002` | `FRAME_TOO_LARGE` | connection-fatal, not retryable |
| `0x0003` | `MALFORMED_MESSAGE` | scope of containing message; connection-fatal during negotiation |
| `0x0004` | `UNSUPPORTED_VERSION` | connection-fatal, not retryable |
| `0x0005` | `DOWNGRADE_DETECTED` | connection-fatal, not retryable |
| `0x0006` | `UNSUPPORTED_CAPABILITY` | connection-fatal, not retryable |
| `0x0007` | `UNSUPPORTED_MESSAGE` | connection-fatal, not retryable |
| `0x0008` | `UNKNOWN_CRITICAL_FIELD` | scope of containing message |
| `0x0009` | `STATE_VIOLATION` | stream-fatal; connection-fatal on stream zero |

| `0x0101` | `INVALID_MANIFEST` | stream-fatal, not retryable unchanged |

Framing errors, bad message IDs, invalid control-stream order, and negotiation
errors are connection-fatal because stream boundaries or shared state are no
longer trustworthy. A semantic error confined to a well-framed transfer
terminates that stream. More than three stream-fatal malformed messages in 60
seconds MUST close the connection.

## 15. Timeouts

Timeouts use a monotonic clock. Only a completely received, authenticated,
state-valid frame counts as progress. Slow or malformed partial input does not
reset a timer.

| Timer | v1.0 limit and action |
| --- | --- |
| First `HELLO` | send within 5 seconds of provisional channel readiness |
| Negotiation | complete through matching ACK within 10 seconds |
| Transport binding | send and verify role-specific finished values within 10 seconds of ACK |
| Frame assembly | complete within 30 seconds of first header octet |
| Manifest progress | at least one valid entry/end every 30 seconds |
| Whole manifest | complete within 300 seconds |
| User decision | accept or reject within 300 seconds of manifest end |
| Data progress | valid chunk, ACK, file end, or commit every 60 seconds |
| ACK progress with outstanding data | 30 seconds |
| Cancel acknowledgement | 10 seconds |
| Idle established connection | send `PING` after 30 seconds |
| `PONG` | matching response within 10 seconds |
| Drain after `GOAWAY` | close after at most 30 seconds |
| Automatic retry budget | five attempts and 120 seconds |
| Resume state | advertised duration, at most 604,800 seconds |

An implementation MAY use a shorter local timeout before an offer starts.
Once a transfer is accepted, shorter timeouts MUST still permit the peer to
meet advertised flow-control limits and MUST produce the machine-readable
`TIMEOUT` result. Timeout cleanup follows cancellation rules.

## 16. Hostile-input failure strategy

All network and discovery input is hostile. A conforming parser and state
machine MUST:

1. Parse the fixed header into checked integers before allocation.
2. Enforce hard and negotiated lengths before reading or allocating bodies.
3. Use incremental checked counters for aggregate counts and sizes.
4. Bound parser memory independently of peer-advertised totals.
5. Reject noncanonical TLV order, duplicates, invalid UTF-8, invalid paths,
   integer overflow, offsets beyond file size, and inconsistent summaries.
6. Verify commitments before commit and use temporary files plus atomic
   destination policy; never follow links.
7. Avoid echoing untrusted bytes, paths, or peer text in errors or logs.
8. Reject all transfer messages before transport-finished completion, rate-limit
   errors, and close immediately when framing, authentication, binding, or
   shared connection state is no longer trustworthy.
9. Make cleanup, cancellation, disconnect, and repeated terminal messages
   idempotent.
10. Never downgrade, guess a type, resynchronize by scanning for `XNNT`, or
    continue after a connection-fatal error.

For an oversized declaration, invalid magic, truncated frame at EOF, or
security failure, the receiver closes without waiting for the declared
remainder. It may omit `ERROR` when sending one is unsafe or would amplify
traffic.

## 17. Compatibility rules

- The established ALPN `xnn-transfer/1` and security profile `0x0001` have the
  immutable byte encodings registered by `pairing-v1.md`. They are not text
  aliases and cannot be silently reinterpreted.
- A major version may change framing or semantics incompatibly. No common
  major fails closed.
- A minor version within a major is backward-compatible. It may add optional
  noncritical fields or capability-gated messages; it may not reinterpret an
  existing field, type, flag, error, or state transition.
- Senders use only fields and messages defined by the selected minor and
  selected capabilities.
- Receivers skip unknown noncritical TLVs, reject unknown critical TLVs, and
  reject unknown messages or flags not enabled by negotiation.
- Numeric IDs, once assigned, are never reused. Removed behavior remains
  reserved.
- Hard limits may be lowered only in a new major version unless negotiation
  already permits the lower value. Raising a limit requires explicit
  capability or minor-version rules and never forces an implementation to
  allocate more than its advertised limit.
- Persisted resume state records the wire major/minor, selected capabilities,
  authenticated peer scope, security profile identifier, manifest
  commitment, and schema version. Incompatible state fails closed.

## 18. Golden vectors

Byte-exact legal and malformed vectors are under `protocol/testdata/v1/`.
Their manifest documents the expected result and stable failure reason.

Run:

```bash
python3 protocol/testdata/v1/validate_vectors.py
python3 protocol/testdata/v1/manifest/validate_vectors.py
python3 protocol/testdata/security/v1/validate_vectors.py
```

The fixture validator is a machine-readable contract for framing, canonical
TLVs, required negotiation fields, per-direction message IDs, role order,
highest-version selection, capability intersection, negotiated limits, and
transport-binding message order. It does not perform TLS exporter or
finished-value verification and is not a production parser or security-profile
test.

The security validator additionally binds the registered ALPN/profile bytes,
canonical `XNNP` first-pairing frames, deterministic application negotiation,
pairing context, decisions, local commit outcomes, hostile controls, and the
exact-pin reconnect's stored floor, kind-`04` transport context, and both
finished values to ADR 0002. It remains fixture evidence rather than a runtime
session or TLS conformance claim.

The protocol-object manifest corpus under
`protocol/testdata/v1/manifest/` covers legal boundaries and rejection before
filesystem access. Its destination comparison profile is explicit fixture
input, not a wire field or negotiated capability, so results do not depend on
the validator host. A non-NFC wire path is rejected before duplicate,
collision, or ancestor comparison. The fixture profiles exercise
case-sensitive POSIX behavior and portable ASCII case collisions for Windows;
they do not replace a destination's complete native Unicode or storage policy.
The validator does not inspect paths on a local filesystem, resolve links,
create files, or establish storage conformance.
